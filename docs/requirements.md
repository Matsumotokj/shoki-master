# 書記マスター（Shoki Master）要件定義書

最終更新: 2026-09-23

---

## 1. 意図（Intent）

秘匿性が高く録音・自動文字起こしが持ち込めない現場（取り調べ、機密会議など）を想定し、
**「聞いて、その場で正確に書き取る／要約する」能力を一人で反復訓練できる環境**を提供する。

題材は生成 AI が動的に作り、採点も自動で行う。そのため教材も採点者も不要で、
何度でも、好きなテーマで練習できる。

---

## 2. 背景と課題

録音・自動文字起こしが許されない現場では、担当者が耳で聞いて書き取る能力を求められる。
しかしその訓練には次の 3 つが必要で、個人で用意するのは難しい。

| 必要なもの | 個人で用意する難しさ |
|---|---|
| リアルな話し言葉の題材 | 書き言葉の文章を読み上げても訓練にならない。毎回新しい題材が要る |
| 音声 | 誰かに読んでもらう必要がある |
| 客観的な採点 | 自分の書き取りが何%正確かを自分では測れない |

本アプリはこの 3 つを自動化する。

---

## 3. 利用者

| 利用者 | 利用シーン | 重視すること |
|---|---|---|
| 訓練者（主たる利用者） | 自分のテーマで問題を作り、繰り返し練習する | 題材の自由度、採点の納得感 |
| 評価者（採用担当者） | URL を開いて数分で「何ができるアプリか」を把握する | **待たずに試せること**、技術的な作りが読み取れること |

評価者は利用者の一種として要件に含める。作問には LLM と音声合成で十数秒かかるため、
待たされると離脱する。**事前生成済みのサンプル問題**を用意して、この導線を分ける。

---

## 4. スコープ

### やること
- テーマ・文字数を指定した題材の自動生成
- 生成した題材の音声化と、文単位の再生制御
- 文字起こしモードの採点（編集距離）と差分表示
- 要約モードの採点（LLM による多軸評価）
- サンプル問題による即時体験
- AWS サーバレス構成でのデプロイと、その構成をコードに残すこと

### やらないこと（と、その理由）
| やらないこと | 理由 |
|---|---|
| ユーザー登録・ログイン | 訓練アプリに必須ではない。閲覧制限は配信層の Basic 認証で足りる |
| 練習履歴の一覧画面 | 認証が無いため「誰の履歴か」を正しく表現できない。データは保存するので将来追加は可能 |
| 複数人での利用・共有 | 個人の訓練が目的 |
| 音声のダウンロード | 生成物は使い捨てとし、1 日で自動削除する |
| 本番／検証の環境分離 | 常設するのは 1 つだけ。使わない仕組みは作らない |

## 5. 機能要件

### F1. 作問

**F1-1** 訓練者は、次を指定して問題を作成できる。

| 項目 | 制約 | 既定値 |
|---|---|---|
| テーマ | 1〜200 文字の自由入力 | なし（必須） |
| 目標文字数 | 50〜500 文字 | 300 |
| 追加の指示 | 0〜200 文字（任意） | 空 |
| 採点モード | 文字起こし / 要約 | 文字起こし |

**F1-2** 生成される題材は、**話し言葉のモノローグ**であること。話者名・括弧・箇条書きを含まない。

**F1-3** 生成された題材は、句点（。！？）で文に分割され、各文の**音声上の開始時刻**が記録される。

**F1-4** 音声は**等速で 1 回だけ**生成される。再生速度は再生時にクライアントで変える。

**F1-5** 作問に失敗した場合、何が起きたかが分かるエラーが表示される。部分的な成功（一部の文だけ音声が無い等）は発生させない。

### F2. 練習

**F2-1** 訓練者は 2 つの練習モードを選べる。

| モード | 挙動 | 位置づけ |
|---|---|---|
| **通し再生** | 音声を最後まで止めずに再生する | 実務条件。取り調べは止められない |
| **句点区切り** | 1 文再生するたびに停止し、操作で次の文へ進む | 初級者向け。書き終えてから次へ進める |

**F2-2** 通し再生モードでは、**N 秒戻るボタン**で聞き直せる（N は 5 秒を想定）。

**F2-3** 句点区切りモードでは、現在の文をもう一度再生できる。

**F2-4** 再生速度は練習中に変更できる。変更しても音声の再生成は起きない。

**F2-5** 読み上げ中の文のテキストは**既定で表示**し、トグルで非表示にできる。
（非表示が書記訓練の本来の姿だが、初見の利用者が戸惑わないよう既定は表示とする）

**F2-6** 訓練者は聞きながらテキストを入力できる。入力は音声の再生状態に影響されない。

**F2-7** ブラウザを再読み込みしても、同じ問題を続けられる（URL に問題 ID を含める）。

### F3. 採点

**F3-1 文字起こしモード**
- 正解文と入力文の**編集距離（Levenshtein）**から正答率を算出する
- 採点前に空白を無視し、全角・半角を統一する
- 句読点とカナの種別（ひらがな／カタカナ）は**区別する**（書き分けも訓練対象のため）
- 誤りの箇所を、正解文・入力文の両方で色分け表示する

**F3-2 要約モード**
- LLM が 3 つの観点で採点する: 忠実性（50 点）、網羅性（35 点）、明瞭・簡潔（15 点）
- 元文にない内容の付け足し（ハルシネーション）を検出した場合、**最終スコアの上限を 70 点**とする
- 要約の長さが元文の 25〜60% の範囲外なら自動減点する（短すぎ・長すぎの 2 段階）
- 採点理由と**模範要約**を提示する

**F3-3** 採点結果には元の題材の全文が含まれ、自分の入力と並べて確認できる。

**F3-4** 同じ問題に何度でも再挑戦できる。

### F4. サンプル問題

**F4-1** 事前生成済みの短いサンプル問題（100 字程度）を 1〜2 問用意し、
**LLM・音声合成を呼ばずに**即座に練習を開始できる。

**F4-2** サンプル問題は文字起こしモード・要約モードの両方を体験できるものとする。

## 6. 非機能要件

### N1. 性能
- **N1-1** 作問（LLM 生成 + 音声合成 + 保存）は 25 秒以内に完了する。
  超える場合は非同期化する（API Gateway のタイムアウトは 29 秒）。
- **N1-2** サンプル問題の開始は 2 秒以内。
- **N1-3** 採点は 10 秒以内（要約モードは LLM 呼び出しを含む）。

### N2. コスト
- **N2-1** 月額 $7（約 ¥1,000）を超えない。
- **N2-2** アクセスが無い月の費用はほぼ 0 とする（常時起動するリソースを持たない）。
- **N2-3** 費用の上限を仕組みで担保する。**バースト制限と総量制限を分ける**:
  - アカウント全体で **1 日 30 問**まで（バースト制限。短時間の集中利用を許しつつ暴走を止める）
  - アカウント全体で **1 か月 200 問**まで（総量制限。これが月額を N2-1 の範囲に収める本体）
  - いずれも超過は 429 を返す
  - API Gateway のスロットリング（2 req/秒、バースト 5）
  - Lambda の同時実行数を 2 に制限
  - AWS Budgets の予算超過時に、生成 AI の呼び出しを自動で拒否する

  1 問あたりの概算: 題材生成 約 0.4 円 + 要約採点 約 0.5 円 + 音声合成 約 1.2 円 = **約 2 円**。
  月 200 問で約 400 円となり、N2-1 の月 $7（約 1,000 円）に収まる。
  日次上限だけでは毎日 30 問で月 900 問（約 1,800 円）となり N2-1 を超えるため、月次上限が必要。

### N3. セキュリティ
- **N3-1** アプリケーションに API キー・シークレットを一切持たない。
  外部サービスへのアクセスはすべて IAM ロールで認可する。
- **N3-2** 生成音声を置くストレージは非公開とし、**有効期限 1 時間の署名付き URL** で配信する。
- **N3-3** 一般公開しない。配信層で Basic 認証を掛ける。
- **N3-4** 利用者の入力文は 1 日で自動削除する。

### N4. 運用
- **N4-1** インフラ構成はすべてコード（AWS SAM）で管理し、リポジトリに残す。
- **N4-2** 実行ログを確認できる。
- **N4-3** 純粋なロジック（採点、文分割、SSML 生成）は自動テストで担保する。
- **N4-4** 自動テストは課金の発生する外部サービス（Bedrock / Polly / S3 / DynamoDB）を呼ばない。
  外部サービスのアダプタは偽のクライアントを差し込んで検証し、実サービスを使う確認は
  `backend/scripts/` の手動実行スクリプトに限定する。

### N5. 可用性
- **N5-1** ベストエフォート。個人の練習用途であり、SLA は定めない。
- **N5-2** ただし一部の失敗で画面が壊れないこと（F1-5）。

## 7. 制約・前提

| # | 内容 |
|---|---|
| C1 | AWS の既存アカウント 1 つで構築する。リージョンは東京（ap-northeast-1）を基本とする |
| C2 | 生成 AI は Amazon Bedrock、音声合成は Amazon Polly を使う（AWS への統一が本プロジェクトの目的の一つ）。Bedrock は**日本国内で完結する推論プロファイル**（`jp.` 接頭辞）を使う ── 機密性の高い業務を想定したアプリであるため |
| C3 | 環境は 1 つだけ。dev / prod の分離はしない |
| C4 | 認証基盤は導入しない |
| C5 | 常設期間は約半年。その後は削除を検討する |

## 8. 実装単位（Unit）

「動くものが 1 つ増える」粒度で分割し、**バックエンドから、未知の大きいものから**着手する。
番号は着手順。

| Unit | 内容 | 状態 |
|---|---|---|
| **U1** | 採点ロジック（編集距離・差分・長さ減点） | ✅ 完了 |
| **U2** | 題材生成・要約採点（Bedrock） | ⏸ アカウント検証待ち |
| **U3** | 文分割と SSML 生成 | 着手中 |
| **U4** | 音声合成（Polly: 音声 + 文ごとの開始時刻） | |
| **U5** | 永続化（DynamoDB に問題と回答、S3 に音声、署名付き URL） | |
| **U6** | API 組み立て（3 エンドポイント + 日次上限） | |
| **U7** | サンプル問題 | |
| **U8** | インフラ（SAM でデプロイ） | |
| **U9** | フロント: 作問画面 | |
| **U10** | フロント: 練習画面（2 モード・速度・表示切替） | |
| **U11** | フロント: 結果画面（差分表示・スコア内訳） | |
| **U12** | 配信（S3 + CloudFront + Basic 認証） | |
| **U13** | CI/CD、README、構成図 | |

着手順の理由: 最も未知が大きい U2（Bedrock が東京で使えるか、日本語の品質、レイテンシ）を先に潰す。
ここで問題が出ると設計が変わるため、早いほど傷が浅い。U3・U4・U5 は互いに独立。

## 9. API 仕様（概要）

| メソッド | パス | 用途 |
|---|---|---|
| `POST` | `/api/problems` | 作問。テーマ等を受け取り、題材・音声 URL・文ごとの開始時刻を返す |
| `GET` | `/api/problems/{problem_id}` | 問題の再取得（再読み込み・再挑戦用。署名付き URL は都度再発行） |
| `POST` | `/api/problems/{problem_id}/answers` | 採点。入力文を受け取り、モードに応じた結果を返す |

- 問題 ID はパスで表し、リクエストボディには含めない
- 題材の全文はレスポンスに含める（音声を聞けば分かる情報であり、隠す技術的意味がないため）
